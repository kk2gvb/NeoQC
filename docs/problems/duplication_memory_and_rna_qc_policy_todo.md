## P0 — Пиковое потребление памяти при точном расчёте дупликации

### Проблема

NeoQC сохраняет точный счётчик каждого уникального 50-нуклеотидного префикса.
При OpenMP-обработке каждый поток использует собственную структуру:

```cpp
std::unordered_map<DuplicationKey, uint64_t>
```

`DuplicationKey` содержит три 64-битных слова и занимает 24 байта. Значение
счётчика занимает ещё 8 байт, поэтому полезная нагрузка одной записи составляет
не менее 32 байт.

Фактическая стоимость выше из-за:

- узла `std::unordered_map`;
- указателей и выравнивания;
- служебных данных allocator;
- массива buckets и текущего load factor;
- возможного хранения одинакового ключа в нескольких thread-local maps.

Ориентировочная фактическая стоимость составляет 48–80 байт на одно уникальное
вхождение ключа в thread-local map. Это предварительная оценка, а не измеренный
контракт производительности.

### Дополнительная копия данных

После завершения чтения для каждого анализатора создаётся:

```cpp
std::vector<DuplicationEntry>
```

Один `DuplicationEntry` ориентировочно занимает 32 байта. В этот момент исходные
hash maps всё ещё находятся в памяти.

Древовидное слияние отсортированных векторов временно удерживает:

```text
левый вход + правый вход + новый объединённый результат
```

Поэтому на отдельных стадиях tree merge память под векторы может почти
удваиваться относительно размера итогового массива.

### Усиливающие факторы

- Одинаковая последовательность, попавшая в разные потоки, временно хранится в
  нескольких maps.
- При paired-end анализе одновременно существуют независимые структуры R1 и R2.
- Рост `OMP_NUM_THREADS` увеличивает число thread-local контейнеров и вероятность
  межпоточного дублирования ключей.
- Maps не освобождаются до построения и слияния сортируемых векторов.
- FASTQ batches и строки ридов также занимают память, хотя обычно не являются
  основной составляющей пика.

### Предварительная оценка

Для 50 млн уникальных префиксов одного read-направления:

| Компонент | Оценка |
| --- | ---: |
| Thread-local maps | 2,4–4,0 ГБ |
| `DuplicationEntry` vectors | около 1,6 ГБ |
| Промежуточный merge-result | до 1,6 ГБ |
| Buckets, allocator, FASTQ batch и другие структуры | дополнительно |

Пиковое потребление одного read-направления может приблизиться к 6–8 ГБ. Для
высокосложной paired-end библиотеки возможны пики порядка 10–16 ГБ и выше.

Эти числа нельзя использовать как гарантированный memory requirement до
проведения измерений. Результат зависит от реализации STL, allocator, load
factor, количества потоков, длины и сложности библиотеки, а также реальной
дупликации.

### Запрещённое быстрое решение

Нельзя молча возвращать ограничение в 100 000 уникальных ключей. Это изменит
семантику результата и снова превратит заявленный exact-расчёт в ограниченную
выборку.

Допустимы только:

1. более экономный exact-алгоритм; или
2. отдельные явно названные `exact` и `approximate` режимы с различимыми
   provenance, output contract и статусом результата.

Approximate-результат нельзя маркировать как exact или незаметно подставлять
вместо него.

### План исследования

- [ ] Добавить воспроизводимый memory benchmark с измерением peak RSS.
- [ ] Измерить single-end и paired-end режимы.
- [ ] Проверить библиотеки с низкой, средней и высокой сложностью.
- [ ] Выполнить измерения при нескольких значениях `OMP_NUM_THREADS`.
- [ ] Зафиксировать число ридов, число уникальных префиксов, elapsed time и peak RSS.
- [ ] Проверить размеры `DuplicationKey`, `DuplicationEntry` и фактическую
      стоимость map entry на поддерживаемых toolchain.
- [ ] Построить модель памяти относительно числа уникальных ключей, а не только
      общего числа ридов.
- [ ] Определить безопасный preflight/warning для машины с заданным объёмом RAM.

### Кандидаты на оптимизацию

- [ ] Преобразовывать maps в vectors перемещением данных, если выбранный
      контейнер допускает это без дополнительной полной копии.
- [ ] Освобождать thread-local maps до наиболее затратных стадий tree merge.
- [ ] Исследовать flat/open-addressing hash map с измеряемым выигрышем памяти.
- [ ] Исследовать одну шардированную карту с контролируемой синхронизацией.
- [ ] Отделить число потоков дупликации от числа потоков остальных метрик.
- [ ] Проверить destructive/in-place merge или более экономную схему редукции.
- [ ] Спроектировать exact external-sort режим для машин с ограниченной RAM.
- [ ] При доказанной необходимости спроектировать отдельный approximate-режим.

### Критерии закрытия P0

- Есть воспроизводимый benchmark и таблица peak RSS.
- Определена и документирована память на 1 млн уникальных ключей.
- Для single-end и paired-end опубликованы проверенные требования к RAM.
- Выбранный алгоритм сохраняет exact-семантику либо режим явно называется
  approximate.
- TSV, summary, provenance и QC-оценка различают алгоритмы по стабильному ID.
- Результаты дупликации совпадают с текущим exact-алгоритмом на контрактных
  fixtures и контрольных реальных наборах.
- Есть тест поведения при нехватке памяти или при невозможности безопасного
  запуска.

## P1 — Отсутствие научно утверждённого RNA-seq ruleset

### Проблема

Текущий профиль:

```text
fastqc-compatible-v1
library_type: generic
```

является воспроизводимым техническим baseline. Он не является утверждённой
RNA-seq policy, автоматическим acceptance gate или клиническим заключением.

FastQC-compatible пороги полезны для первичной диагностики, но часть флагов для
RNA-seq может отражать нормальные свойства библиотеки, а не технический дефект.

### Метрики, требующие RNA-seq интерпретации

#### Per base sequence content

Выраженное смещение состава первых позиций может быть связано с
random-hexamer priming, способом подготовки библиотеки и другими ожидаемыми
protocol-specific эффектами.

#### Per sequence GC content

Транскриптом представляет собой смесь неодинаково экспрессируемых транскриптов.
Поэтому наблюдаемое распределение GC может отличаться от простой нормальной
модели без обязательного ухудшения пригодности данных.

#### Sequence duplication

Высокоэкспрессируемые транскрипты создают биологическую дупликацию. Высокий
duplication level нельзя автоматически интерпретировать как PCR-артефакт без
учёта library preparation, сложности библиотеки и downstream-результатов.

#### Sequence length distribution

Переменная длина может быть ожидаемой после trimming или для отдельных типов
RNA-библиотек. Для raw reads и cleaned reads могут потребоваться разные правила.

#### Adapter content

Интерпретация зависит от insert size, протокола, длины рида и стадии анализа.

#### Per-base quality и N content

Эти показатели обычно лучше переносятся между типами библиотек, но их пороги
также должны быть валидированы на целевом процессе и оборудовании.

### До появления RNA-профиля

- Использовать `fastqc-compatible-v1` только как явно отображаемый технический
  baseline.
- Показывать идентификатор, версию и hash ruleset в результате.
- Не называть общий статус клиническим заключением.
- Не использовать generic-профиль как автоматический RNA-seq acceptance gate.
- Не заменять historical ruleset при повторном открытии старого результата.
- Не активировать `neoqc-rna-v1` до документированной научной проверки.

### Требования к `neoqc-rna-v1`

- [ ] Разделить или явно параметризовать как минимум `poly(A)`,
      `rRNA depletion`, `total RNA` и `small RNA`.
- [ ] Определить, применяются ли правила к raw reads, cleaned reads или обоим
      состояниям отдельно.
- [ ] Собрать репрезентативный набор RNA-seq библиотек с известным техническим
      качеством и provenance.
- [ ] Сопоставить флаги с downstream-метриками: mapping rate, strandedness,
      rRNA contamination, gene-body coverage и usable reads.
- [ ] Для каждого порога зафиксировать источник, обоснование, единицу измерения,
      оператор сравнения и reason code.
- [ ] Оценить false positive и false negative rates.
- [ ] Проверить поведение на разных read length, sequencing platforms и library
      preparation protocols.
- [ ] Создать версионированный JSON ruleset с SHA-256.
- [ ] Добавить явный выбор профиля через CLI или конфигурацию запуска.
- [ ] Запретить автоматическую или молчаливую замену ruleset.
- [ ] Добавить boundary, malformed-data, regression и real-fixture tests.
- [ ] Провести доменное ревью и зафиксировать ответственное лицо/группу,
      утвердившую policy.

### Критерии закрытия P1

- Для каждого поддержанного типа RNA-библиотеки определена область применимости.
- Пороговые значения имеют документированное научное и эмпирическое обоснование.
- Известны false positive/negative характеристики на контрольном наборе.
- Ruleset имеет стабильные ID, semantic version, hash и reason codes.
- Пользователь явно видит активный профиль в JSON и HTML.
- Старые результаты продолжают ссылаться на исходную версию ruleset.
- Автоматический gate включается только для утверждённого типа библиотеки и
  документированной стадии анализа.
- В интерфейсе сохраняется предупреждение, что технический QC не является
  клиническим заключением.

## Приоритет дальнейшей работы

1. Сначала выполнить P0 benchmarking: риск исчерпания памяти может физически
   блокировать анализ больших библиотек.
2. Не менять exact-семантику до получения измерений и выбора архитектуры.
3. Параллельно подготовить дизайн исследования для RNA-seq ruleset, но не
   активировать новые пороги до доменного утверждения.
4. После реализации обновить этот документ фактическими измерениями, ссылками
   на коммиты, версиями алгоритмов и решением по каждому checkbox.
