# Запрос: интеграция NeoQC как замены FastQC/fastp и ускорителя S01–S03

Этот документ — техническое задание для разработчика NeoQC
(`https://github.com/kk2gvb/NeoQC`), описывающее, что нужно от инструмента,
чтобы он занял место текущего FastQC/Cutadapt-стека в NeoMRNA-Vax и снял
задокументированное узкое место в S01–S03. Все цифры и утверждения ниже
взяты из измерений и кода пайплайна, а не являются предположениями.

Задачи разбиты на три приоритета — P0, P1, P2 — по убыванию отношения
"выигрыш к риску переделки уже рабочей инфраструктуры".

---

## Глоссарий

| Термин | Значение |
|---|---|
| **FASTQ** | Текстовый формат хранения прочтений секвенатора: 4 строки на запись — заголовок, последовательность нуклеотидов, разделитель, качество каждого нуклеотида. |
| **R1/R2 (paired-end)** | Секвенатор читает фрагмент с двух концов — получаются два файла-напарника, где запись №N в R1 обязана соответствовать записи №N в R2. |
| **Phred33 / качество** | Каждый нуклеотид имеет оценку уверенности секвенатора, закодированную одним ASCII-символом. Q30 соответствует вероятности ошибки 1 на 1000; чем выше Q, тем надёжнее база. |
| **GIL** | Особенность Python: только один поток исполняет байткод в конкретный момент, даже на многоядерном CPU. Из-за этого чистый Python-код не ускоряется добавлением потоков — нужен отдельный процесс на ядро либо компилируемый язык, явно освобождающий GIL. |
| **Checkpoint / identity** | Пайплайн не пересчитывает готовую работу повторно — сверяет отпечаток (SHA-256 + версия инструмента + параметры команды) с тем, что требуется сейчас, и переиспользует результат при совпадении. |
| **Fail-closed** | Если что-то не может быть однозначно проверено — пайплайн останавливается с ошибкой, а не продолжает с предположением "наверное, всё в порядке". |
| **Bounded-memory streaming** | Обработка файла потоком, без загрузки его целиком в память — важно для файлов по 10–40 ГБ на образец. |
| **Provenance** | Полная запись того, каким инструментом, какой версии, с какими параметрами и на основе каких входных хэшей получен каждый артефакт. |
| **QC Gate** | Точка в пайплайне, где по метрикам качества принимается решение: продолжать / нужна доп. обработка / остановить как непригодные данные. |

## Текущая архитектура

### Два независимых пути QC

В проекте существуют два независимых куска кода, оба называются "проверка
качества сырых FASTQ" (S02 raw_qc), но сильно отличаются по зрелости — и
это стоит знать до начала проектирования замены, чтобы не ориентироваться
на менее значимый из них.

Первый — `RawQCHandler` (`local/stages/raw_qc.py`), используется общим CLI
`mrna-vax run`. Он тонкий: один вызов `fastqc` на все файлы разом, без
`--threads`, без фиксации версии инструмента. Парсер
(`local/stages/parsers/fastqc.py`) регэкспом вытаскивает всего 4 поля:
общее число прочтений, `%GC`, суррогатную оценку "Q30%" (усреднение
качества первых 10 позиций прочтения, пересчитанное по формуле
`avg/40.0*100` — это не настоящая доля баз с качеством ≥Q30, а грубая
аппроксимация) и процент дупликации. Решение принимается по двум порогам.

Второй — `ReadPreparationService` (`read_preparation/`), используется
выделенным CLI `mrna-vax prepare-reads`, и именно этот путь обрабатывал
всех реальных пациентов. Здесь версия FastQC зафиксирована (`0.11.9`),
запуск защищён файловой блокировкой, результат публикуется атомарно, а при
повторном запуске старый результат переиспользуется только при полном
совпадении входных данных, версии инструмента и параметров команды.
Парсер (`fastqc_parser.py`, 885 строк) разбирает все 11 модулей отчёта
FastQC в строго типизированную структуру и явно падает с понятным кодом
ошибки на любом неожиданном формате, вместо того чтобы подставлять пустое
значение. Результат приводится к строгой JSON Schema
(`normalized_qc_metrics.schema.json`, лишние поля запрещены наравне с
отсутствующими обязательными).

Поверх метрик работает формальный движок принятия решений
`QCPolicy`/`QCDecision` (`neo_mrna_vax_core/qc/policy.py`, 469 строк) — 9
независимых правил: совместимость кодировки качества между R1/R2,
минимальное число пар прочтений, доля прочтений хорошего качества Q20/Q30,
длина "плохого хвоста" прочтения, доля адаптерных последовательностей,
доля неопределённых нуклеотидов N, дупликация, неожиданная контаминация.
Каждое правило возвращает не просто "плохо/хорошо", а код причины,
рекомендацию по исправлению (обрезка адаптеров, обрезка по качеству) и
конкретные цифры-основание. Решения агрегируются от файла к библиотеке, к
образцу, к пациенту, а сама политика версионирована и зафиксирована по
SHA-256, так что порог нельзя случайно поменять незаметно для остальной
команды.

Отсюда практический вывод для NeoQC: путь с движком решений переписывать
не нужно и не стоит — он уже откалиброван под наш протокол (Illumina
paired-end 100bp, WES + RNA-seq) и покрыт десятками негативных тестов на
битые входные данные. Роль NeoQC — быть источником метрик, заменяя FastQC
как вычислительный инструмент, при этом решения по-прежнему принимает
существующий `QCPolicy`.

### Обрезка адаптеров: сейчас Cutadapt, не fastp

S03 preprocessing использует `CutadaptAdapter`
(`read_preparation/preprocessing_adapter.py`), обёртку вокруг Cutadapt 4.9,
c фиксированными параметрами команды:

```
cutadapt --cores 8 --report full \
  -q <quality_cutoff_r1_low>,<quality_cutoff_r1_high> \
  -Q <quality_cutoff_r2_low>,<quality_cutoff_r2_high> \
  -a <adapter_r1_IUPAC_sequence> \
  -A <adapter_r2_IUPAC_sequence> \
  --minimum-length <minimum_length> \
  --pair-filter any \
  --json <report.json> \
  --output <r1_output.fastq.gz> \
  --paired-output <r2_output.fastq.gz> \
  <r1_input> <r2_input>
```

По умолчанию: `quality_cutoff = (0, 20)` для обеих сторон,
`minimum_length = 50`, `pair_filter = "any"` (пара отбрасывается целиком,
если хотя бы одна сторона не прошла фильтр), `cores = 8`. Адаптерные
последовательности задаются как IUPAC-строки, профиль и его SHA-256
фиксируются в execution lock.

Если цель NeoQC — "заменить fastp", это стоит уточнить сразу: имеется в
виду замена той же функции (обрезка под наши текущие параметры Cutadapt)
или принятие fastp-подобной модели, где обрезка и QC происходят за один
проход — это два принципиально разных по объёму задания.

### Главный измеренный bottleneck

После того как Cutadapt обрезает адаптеры, пайплайн заново, с нуля,
построчно проверяет получившийся файл — читает каждую запись, сверяет её
корректность и синхронность между R1 и R2. Эта повторная проверка
написана на чистом Python и работает медленно — настолько, что она в разы
дольше самой обрезки.

Реальный прогон `P1VAL-NOMHCALT-20260820T051047Z` дал точную разбивку:
S03 preprocessing занял ~2ч48м, из них сам Cutadapt — ~6 минут, а
**~2ч09м — построчная Python-ревалидация** очищенного FASTQ сразу после
него. Узкое место локализовано в одной реализации
(`intake/fastq.py::_records`), которая используется в трёх местах: при
первичном приёме сырых данных (S01), при проверке checkpoint перед
повторным использованием готового результата (S03) и сразу после
Cutadapt (S03, основной источник тех самых 2ч09м).

Мы уже пробовали ускорить это "в лоб" через параллельные потоки
(`ThreadPoolExecutor`) — стало в 3 раза медленнее (2.39–2.46 МиБ/с против
6.75 МиБ/с однопоточного варианта), а не быстрее. Причина в GIL: чтение и
распаковка файла честно освобождают блокировку, потому что реализованы на
C, а вот сам построчный разбор каждой записи — чистый Python-цикл, который
держит GIL почти всё время работы. Добавление потоков в такой ситуации
даёт только накладные расходы на переключение контекста, без реального
параллелизма. Единственный работающий путь ускорения — компилируемый
streaming-парсер, и это ровно то, чем NeoQC уже занимается по своему
описанию: строгая проверка структуры FASTQ и синхронности R1/R2.

## P0 — заменить `validate_paired_fastq` на ядро NeoQC

Это самый большой измеримый выигрыш из всего списка, и решение "нужен
компилируемый парсер" уже согласовано в проекте независимо от этого
запроса.

Задача: NeoQC должен прочитать пару файлов R1/R2 (обычных или gzip),
построчно проверить физическую корректность каждой записи, убедиться, что
запись №N в R1 и запись №N в R2 — действительно напарники, посчитать по
пути статистику и SHA-256 каждого файла — всё за один проход, без загрузки
файла целиком в память, поскольку реальные файлы достигают 10–40 ГБ. При
любом нарушении обработка должна немедленно останавливаться с понятным
кодом ошибки, а не продолжаться с предположением "наверное, сойдёт".

### Вход

| Параметр | Тип | Описание |
|---|---|---|
| `r1_path`, `r2_path` | путь к файлу | FASTQ или FASTQ.GZ (возможно несколько конкатенированных gzip-членов подряд — штатная практика при слиянии лейнов секвенатора). Должны указывать на два физически разных файла — проверка не только по имени пути, но и по inode. |
| `alphabet` | строка | Допустимый алфавит нуклеотидов, по умолчанию `ACGTN`, регистронезависимо. |
| `quality_encoding` | enum | Сейчас поддерживается только `phred33` (ASCII-диапазон 33–126). |
| `declared_sha256` | hex-строка, 64 символа, опционально | Если передан заранее известный хэш — после вычисления сверяется, при несовпадении обработка завершается ошибкой. |
| `chunk_size` | целое число, байты | Размер блока чтения за системный вызов; влияет только на память, не на корректность. |

### Выход

По каждому файлу (R1 и R2 отдельно):

| Поле | Тип | Смысл |
|---|---|---|
| `size_bytes`, `mtime_ns`, `device`, `inode` | числа | Снимок состояния файла до чтения, сверяется повторно после — изменение файла во время обработки является ошибкой. |
| `sha256` | hex-строка | Потоковый хэш всего файла, сырых байт на диске, до распаковки. |
| `compression` | `"gzip"` \| `"none"` | Определяется по расширению `.gz`. |
| `gzip_member_count` | int или `null` | Число конкатенированных gzip-членов. |
| `record_count` | int | Число обработанных записей. |
| `minimum_read_length`, `maximum_read_length` | int | Мин/макс длина прочтения. |
| `minimum_quality_ascii`, `maximum_quality_ascii` | int | Мин/макс встреченный код качества. |
| `base_count` | int | Суммарное число нуклеотидов. |
| `length_histogram` | список пар (длина, количество) | Распределение длин прочтений. |

По паре в целом: `paired_record_count` — число успешно сопоставленных пар;
`read_id_mismatches`, `mate_flag_mismatches` — счётчики несовпадений
(текущая реализация останавливается на первом же несовпадении, поэтому
на практике они всегда равны нулю к моменту успешного завершения — см.
открытый вопрос ниже).

### Проверки и обязательные тесты

Ниже — полная матрица приёмочных тестов: для каждого правила указано
условие срабатывания, минимальный пример, который обязан провалиться, и
пример, который похож, но обязан пройти — чтобы проверка не оказалась
избыточно строгой. Часть сценариев уже покрыта существующим тестовым
набором NeoMRNA-Vax; остальные нужно реализовать в тестах NeoQC с нуля.
Каждая строка таблицы — это отдельный юнит-тест.

**Структура gzip-потока**

| Условие | Обязан упасть | Обязан пройти | Покрытие |
|---|---|---|---|
| Файл `.gz` не начинается с gzip-сигнатуры (`\x1f\x8b`) | Файл, начинающийся с произвольных байт | Файл с корректной сигнатурой | есть тест |
| После валидного gzip-члена идут байты, сами не являющиеся началом нового члена | Валидный `.fastq.gz` + произвольный "мусор", дописанный в конец | Несколько **конкатенированных** валидных gzip-членов подряд — это норма, не ошибка (типичный случай слияния лейнов) | есть тест |
| Файл обрывается посреди незавершённого gzip-члена | Валидный заголовок, часть сжатых данных, файл обрезан | Полный, не обрезанный gzip-член | нет теста |
| Контрольная сумма распакованных данных не совпадает с записанной в trailer | Испорченные сжатые байты в теле при валидном заголовке | Неповреждённый gzip-член | нет теста |
| Файл `.gz` не содержит ни одного gzip-члена | Файл нулевой длины | Файл хотя бы с одним валидным членом | нет теста |

Самая частая практическая ошибка при реализации с нуля — по умолчанию
трактовать конкатенацию нескольких gzip-членов как "мусор после первого
члена". Это штатный случай, а не ошибка, и он уже подтверждён отдельным
тестом в текущей реализации — обязательно воспроизвести это поведение.

**Структура отдельной записи**

| Условие | Обязан упасть | Обязан пройти | Покрытие |
|---|---|---|---|
| После заголовка не хватает одной или нескольких из оставшихся трёх строк | `@READ1` / `ACGTN` / `+` — без строки качества | Полная четырёхстрочная запись | нет теста |
| Заголовок не начинается с `@`, либо состоит из одного `@` без идентификатора | `READ1\n...` (нет `@`) или `@\n...` (пустой ID) | `@READ1\n...` | нет теста |
| Последовательность пустая | `@READ1\n\n+\n\n` | `@READ1\nACGTN\n+\nIIIII\n` | нет теста |
| Последовательность содержит символы вне алфавита | Символ `X` в последовательности | Строчные буквы (`acgtN`) допустимы | нет теста |
| Разделитель не начинается с `+` | `@READ1\nACGTN\n-\nIIIII\n` | `@READ1\nACGTN\n+\nIIIII\n` | нет теста |
| После `+` есть непустой текст, не совпадающий с заголовком | Заголовок `READ1`, разделитель `+OTHER` | Пустой разделитель или разделитель, дублирующий заголовок | есть тест |
| Длина последовательности не равна длине качества | 5 нуклеотидов, 3 символа качества | Равные длины | нет теста |
| Строка качества пустая | `@READ1\nACGTN\n+\n\n` | Непустая строка той же длины | нет теста |
| Символ качества вне ASCII-диапазона 33–126 | Код ASCII 32 или ниже, либо выше 126 | Все символы строго в диапазоне `!`–`~` | нет теста |
| Во всём файле ноль записей | Пустой `.fastq`-файл | Файл хотя бы с одной записью | нет теста |

Записи разной длины внутри одного файла — норма (гистограмма длин должна
отражать оба значения), это уже проверено отдельным тестом.

Отдельный нюанс: текущая реализация использует один и тот же код ошибки и
для пустой строки качества, и для выхода символа за допустимый диапазон.
Необязательно повторять это буквально — можно завести два разных кода — но
это стоит явно решить и задокументировать заранее, поскольку downstream-код
интерпретирует конкретную причину сбоя.

**Синхронизация пары R1/R2**

| Условие | Обязан упасть | Обязан пройти | Покрытие |
|---|---|---|---|
| Пути R1 и R2 указывают на один и тот же файл (по пути или по inode) | Один путь передан дважды, либо один файл — симлинк на другой | Два физически разных файла | нет теста |
| Идентификатор прочтения в заголовке пуст | `@ 1:N:0:INDEX\n...` | `@READ1 1:N:0:INDEX\n...` | нет теста |
| Суффикс `/1`/`/2` и CASAVA-поле в одном заголовке указывают на разное направление | `@READ1/1 2:N:0:INDEX\n...` | Оба способа согласны, либо указан только один | нет теста |
| Число записей в R1 не равно числу записей в R2 | R1 — 2 записи, R2 — 1 запись | Равное число записей | есть тест (базовый happy-path) |
| Канонические идентификаторы записи №N в R1 и R2 не совпадают | `READ1` в R1, `READ2` в R2 на той же позиции | Одинаковый базовый ID в обеих записях | есть тест |
| Направление по заголовку не соответствует физическому файлу-источнику | Запись из R1-файла с флагом направления "2" | Запись из R1-файла с флагом "1" или без явного флага | нет теста |

Синхронизация выполняется построчно, "в ногу", без хранения полного
набора идентификаторов в памяти — это принципиально важно на больших
WGS-файлах.

**Целостность файла и провенанс**

| Условие | Обязан упасть | Обязан пройти | Покрытие |
|---|---|---|---|
| Запрошена кодировка качества, отличная от `phred33` | `quality_encoding="phred64"` | `quality_encoding="phred33"` (по умолчанию) | нет теста |
| Путь указывает не на обычный файл | Путь к директории | Путь к обычному файлу | нет теста |
| Состояние файла на диске изменилось за время обработки | Файл дописан после снятия начального снимка, до завершения чтения | Файл, неизменный на протяжении всей проверки | нет теста |
| Заранее заданный хэш не совпадает с фактическим | `declared_sha256`, не совпадающий с содержимым | Совпадающий хэш либо параметр не передан | есть тест |

Одно из существующих требований — потоковая, а не "в память целиком"
природа обработки — уже подтверждена косвенно: callback прогресса должен
вызываться многократно по мере продвижения по файлу, а не один раз в
конце.

**Требования к самим тестам, не только к проверкам:** каждый негативный
тест обязан проверять точный код ошибки, а не просто факт падения; рядом
с каждым негативным тестом обязателен позитивный на похожий, но валидный
вход — иначе нет уверенности, что проверка не избыточно строгая; отдельно
нужен тест на реальную потоковую обработку, где заведомо большой файл не
вызывает пропорционального роста памяти процесса; и обязателен тест на
многочленный gzip — это частый штатный сценарий при слиянии лейнов, а не
редкий edge-case.

**Открытый вопрос.** Текущая реализация останавливается на первом же
найденном несоответствии — не пытается собрать полный список всех проблем
за один проход. Стоит решить с командой NeoMRNA-Vax, сохранять ли это
поведение (быстрее, но при ошибке видна только первая причина) или
добавить режим полного прохода с отчётом обо всех найденных
несоответствиях (медленнее, но полезнее один раз при внедрении). Если
выбран второй вариант, набор тестов нужно дополнить кейсами на несколько
одновременных ошибок в одном файле — ни одна не должна маскировать
другую.

## P1 — метрики NeoQC в формате `NormalizedReadMetrics`

Замена FastQC сама по себе не даёт такого выигрыша по времени, как P0:
расчёт QC-метрик прямо помечен в проекте как не текущее узкое место —
12.5 минут на 6 файлов при измеренном baseline, оптимизация S01/S03/S04
явно приоритетнее. Ценность здесь — в точности (настоящий Q30% вместо
суррогата, точный, а не сэмплированный расчёт дупликации) и в снятии
зависимости от внешнего Perl/Java-инструмента.

Суть задачи: сейчас числа, по которым принимается решение "образец
достаточно хорош, чтобы продолжать" или "нужна доп. очистка", считает
FastQC, а наш код только интерпретирует его отчёт. Мы не просим NeoQC
решать, хорош образец или нет — это уже делает `QCPolicy`. Мы просим
NeoQC считать те же самые числа (долю адаптеров, долю неопределённых
нуклеотидов, долю прочтений хорошего качества, дупликацию), но точнее и
быстрее — и отдавать их в формате, который наш код уже умеет читать.

### Вход

Тот же, что для P0: пара или одиночный FASTQ/FASTQ.GZ, плюс контекст
запуска — `sample_id`, `physical_unit_id`, `assay` (`WES`/`WGS`/`RNA_SEQ`
— влияет на пороги дальнейшей оценки, не на сам расчёт), `phase` (`raw`
до обрезки или `cleaned` после Cutadapt).

### Выход — целевая структура `NormalizedReadMetrics`

| Поле | Тип | Диапазон | Смысл |
|---|---|---|---|
| `read_pair_count` | int / `null` | `>0` | Число пар прочтений. |
| `base_count` | int / `null` | `>0` | Суммарное число нуклеотидов. |
| `adapter_fraction_max` | float | `0–1` | Максимальная доля адаптера по любому циклу. |
| `adapter_fraction_last_cycle` | float / `null` | `0–1` | Доля адаптера на последнем цикле — индикатор недообрезанности 3'-конца. |
| `n_fraction_max` | float | `0–1` | Максимальная доля "N" по любому циклу. |
| `mean_n_fraction` | float / `null` | `0–1` | Средняя доля "N" по всем циклам. |
| `median_read_length` | float | `>0` | Медианная длина прочтения. |
| `minimum_read_length`, `maximum_read_length` | int / `null` | `>0` | Мин/макс длина. |
| `gc_fraction` | float / `null` | `0–1` | Доля GC. |
| `fraction_reads_mean_q20` / `fraction_reads_mean_q30` | float / `null` | `0–1` | Доля прочтений со средним качеством ≥Q20/Q30 — это и есть настоящий Q30%. |

### Задачи

Каждый расчёт NeoQC (per-cycle quality, per-base content, GC/N
distribution, duplication, overrepresented sequences, adapter content —
всё уже заявлено в README NeoQC) нужно сопоставить с полем из таблицы
выше. Сам движок `QCPolicy`/`QCDecision` трогать не нужно — задача
ограничена источником входных метрик.

Отдельного решения требует дупликация: NeoQC считает её точно (хранит все
уникальные 50-нуклеотидные префиксы), тогда как FastQC использует
сэмплированную оценку — это разные числа для одного и того же файла даже
без ошибок в реализации. Подставить новый источник данных под старые
пороги `QCPolicy` (0.70 для DNA, 0.85 для RNA) без перекалибровки нельзя —
иначе решения PASS/WARN/FAIL начнут массово меняться без научного
обоснования. Также нужно определить, откуда берётся `evidence_artifact`
для NeoQC-варианта — сейчас это путь к отчёту FastQC, для NeoQC это будет
путь к его собственному выводу.

## P2 — роль относительно Cutadapt/fastp

fastp обычно объединяет QC и обрезку адаптеров в один проход по файлу —
архитектурно привлекательно, но в нашем пайплайне сейчас это отдельные
стадии с раздельными артефактами и схемами: QC сырых данных → обрезка →
повторная проверка → QC очищенных данных. Замена только исполнителя (тот
же Cutadapt, но быстрее) — гораздо меньшая по объёму задача, чем смена
самой модели работы пайплайна.

Это нужно решить с разработчиком NeoQC явно, а не по умолчанию: цель —
инструмент, который делает то же самое, что Cutadapt, под наши текущие
параметры, просто быстрее? Или принципиально другая модель, где один
проход сразу чистит данные и считает QC-метрики после чистки? Второе — не
техническая деталь, а изменение структуры пайплайна: сейчас между "почистили"
и "проверили, что почистилось правильно" стоит отдельный, независимо
проверяемый шаг — намеренно, ради надёжности и возможности переиграть
только одну часть при сбое.

### Вход и выход, если выбрана замена функции Cutadapt

Вход: исходные R1/R2, адаптерные последовательности для обеих сторон в
формате IUPAC, нижний/верхний Phred-порог обрезки по качеству для каждой
стороны (по умолчанию 0–20), минимальная длина после обрезки, ниже которой
пара отбрасывается целиком (по умолчанию 50), правило отбрасывания пары
`any` — пара отбрасывается, если хотя бы одна сторона не прошла фильтр.

Выход: очищенные gzip-сжатые R1/R2 и JSON-отчёт, включающий как минимум
число прочтений с обнаруженным и обрезанным адаптером по каждой стороне и
общее число входных пар — для сверки, что число обрезанных не превышает
число входных (это уже есть как защитная проверка в текущем коде).

В любом варианте результат обрезки должен допускать полную повторную
проверку через логику P0 — это часть fail-closed архитектуры пайплайна, а
не предмет для переговоров.

## Ограничение, которое стоит обсудить заранее

NeoQC сейчас считает метрики в один поток. Для P0 это не критично — наш
пайплайн и так не распараллеливает работу внутри одного процесса, а
запускает несколько независимых процессов параллельно (по одному на
файл), что не упирается в ограничение Python. Но стоит уточнить у
разработчика, планируется ли многопоточность внутри самого NeoQC
(например, через OpenMP, уже упомянутый в README) — от ответа зависит,
сколько экземпляров NeoQC можно безопасно запускать одновременно под
имеющийся бюджет CPU и памяти.

Отдельно стоит заранее уточнить memory footprint точного расчёта
дупликации: он хранит в памяти все уникальные 50-нуклеотидные префиксы, и
это единственное место во всём NeoQC, которое по описанию в его README
выглядит потенциально проблемным при масштабировании на реальные объёмы
данных лаборатории — наши tumor/normal DNA файлы достигают десятков
гигабайт.

## Что мы выигрываем

Если закрыт только P0, самый долгий и при этом самый техничный, не
научный, шаг во всём цикле S01–S04 станет в разы быстрее — потому что
сейчас это единственное место, где мы уже перепробовали штатные способы
ускорения и упёрлись в стену. В цифрах: экономия порядка двух часов на
образец с обрезкой в S03, и пропорционально — в S01, где полная валидация
33 ГиБ заняла 1ч18м с той же самой основной статьёй затрат. Для полного
цикла S01–S04 (чистое время сейчас ~6ч36м без сбоев) это реалистично на
1.5–2.5 часа короче на том же железе — сокращение времени до результата
почти на треть, и именно на самом затратном узле во всём измеренном
профиле.

Если дополнительно закрыт P1, отчётность получает настоящий Q30% вместо
суррогатной оценки по первым 10 циклам и точную, а не сэмплированную
дупликацию — при условии согласованной перекалибровки порогов. Пайплайн
теряет зависимость от внешнего Perl/Java-бинарника в пользу инструмента,
который лаборатория пишет и может развивать сама, и получает единый
self-contained HTML-отчёт вместо отдельного шага агрегации MultiQC.

Если дополнительно закрыт P2 в модели "обрезка и QC за один проход",
устраняется не только сама ревалидация, но и необходимость в отдельном
постпроцессном проходе после обрезки — самый архитектурно смелый, но и
самый выигрышный по времени сценарий, при условии, что решение о смене
границы стадий будет принято осознанно, отдельным проектированием, а не
как побочный эффект интеграции инструмента.

В сумме NeoQC, реализованный по этому списку, закрывает единственный узел
во всём цикле S01–S04, для которого в проекте уже официально
зафиксировано отсутствие штатных решений в рамках текущего стека — и
делает это инструментом, который лаборатория разрабатывает и
контролирует сама, а не внешней зависимостью с непрозрачной для нас
скоростью развития.
